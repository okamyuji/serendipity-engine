# システム設計書

## 概要

Serendipity Engine は、Rails 8 API バックエンドと
React 18 フロントエンドで構成されるナレッジプラットフォームです。
pgvector を使用したセマンティック検索と AI による発見機能を提供します。

## アーキテクチャ原則

### 関心の分離

各レイヤーの責務を明確に分離しています。

- コントローラー: HTTP リクエストの処理とレスポンスの生成
- サービス: ビジネスロジックの実装
- モデル: データの永続化とバリデーション
- ジョブ: 非同期処理の実行

### スケーラビリティ

水平スケーリングを考慮した設計を採用しています。

- ステートレスな API 設計
- バックグラウンドジョブによる負荷分散
- キャッシュの活用
- データベースのインデックス最適化

### テスタビリティ

テストしやすい設計を重視しています。

- 依存性注入の活用
- モックとスタブの使用
- 単体テストと統合テストの分離
- VCR による外部 API のモック化

## システム構成

### レイヤー構造

以下の4つのレイヤーで構成されます。

1. プレゼンテーション層: React フロントエンド
2. API 層: Rails コントローラー
3. ビジネスロジック層: サービスオブジェクト
4. データ層: PostgreSQL + pgvector

### コンポーネント図

主要なコンポーネントは以下の通りです。

- フロントエンド
  - React 18 + Vite
  - TanStack Query（サーバー状態管理）
  - Zustand（クライアント状態管理）
  - React Flow（グラフ可視化）

- バックエンド
  - Rails 8 API
  - Devise + JWT（認証）
  - Solid Queue（ジョブ処理）
  - Neighbor gem（ベクトル検索）

- データストア
  - PostgreSQL 16 + pgvector
  - Redis（キャッシュ・セッション）

- 外部サービス
  - OpenAI API（Embedding生成）

## データフロー

### ノート作成フロー

以下の流れでノートが作成されます。

1. ユーザーがフロントエンドでノートを作成します
2. API リクエストが NotesController に送信されます
3. ノートがデータベースに保存されます
4. EmbeddingJob がキューに追加されます
5. バックグラウンドで Embedding が生成されます
6. ConnectionBuildJob がキューに追加されます
7. バックグラウンドでコネクションが構築されます

### セマンティック検索フロー

以下の流れで検索が実行されます。

1. ユーザーが検索クエリを入力します
2. API リクエストが SearchController に送信されます
3. EmbeddingService がクエリの Embedding を生成します
4. Neighbor gem が類似チャンクを検索します
5. チャンクからノートを取得します
6. 類似度スコアを付与します
7. 結果をフロントエンドに返します

### 発見生成フロー

以下の流れで発見が生成されます。

1. DailyDiscoveryJob が毎日午前6時に実行されます
2. 各ユーザーに対して DiscoveryEngine が実行されます
3. 忘れられた宝石を検出します
4. クロスドメインブリッジを検出します
5. 最近の関連性を検出します
6. 発見をデータベースに保存します
7. ユーザーが発見を閲覧します

## データベース設計

### 正規化

第3正規形までの正規化を実施しています。

- 重複データを排除します
- 更新異常を防止します
- データの整合性を保証します

### インデックス戦略

以下のインデックスを設定しています。

- 主キーインデックス: 全テーブル
- 外部キーインデックス: 全リレーション
- 複合インデックス: 頻繁に使用されるクエリ
- HNSW インデックス: ベクトル検索

### パーティショニング

将来的なデータ増加に備えて以下を検討します。

- access_logs テーブルの日付パーティショニング
- chunks テーブルのユーザーパーティショニング

## セキュリティ設計

### 認証と認可

以下の仕組みで認証と認可を実施します。

- JWT トークンによるステートレス認証
- トークンの有効期限は24時間
- ログアウト時にトークンを無効化
- ユーザーは自身のリソースのみにアクセス可能

### データ保護

以下の対策でデータを保護します。

- パスワードは bcrypt でハッシュ化
- API キーは環境変数で管理
- 本番環境では Rails credentials で暗号化
- HTTPS 通信を強制

### 入力検証

以下の検証を実施します。

- Strong Parameters による許可リスト方式
- モデルレベルでのバリデーション
- SQL インジェクション対策
- XSS 対策

## パフォーマンス設計

### キャッシュ戦略

以下のキャッシュを実装します。

- Redis によるセッションキャッシュ
- クエリ結果のキャッシュ
- Embedding のキャッシュ
- API レスポンスのキャッシュ

### 非同期処理

以下の処理を非同期化します。

- Embedding 生成
- コネクション構築
- 発見生成
- メール送信

### データベース最適化

以下の最適化を実施します。

- N+1 クエリの防止（includes の使用）
- インデックスの適切な設定
- クエリの最適化
- コネクションプーリング

## エラーハンドリング

### エラーの分類

以下のようにエラーを分類します。

- バリデーションエラー: HTTP 422
- 認証エラー: HTTP 401
- 認可エラー: HTTP 403
- リソース不在エラー: HTTP 404
- サーバーエラー: HTTP 500

### エラーログ

以下の情報をログに記録します。

- エラーメッセージ
- スタックトレース
- リクエスト情報
- ユーザー情報
- タイムスタンプ

### リトライ戦略

以下のリトライ戦略を採用します。

- OpenAI API エラー: 最大3回、指数バックオフ
- ネットワークエラー: 最大3回、指数バックオフ
- データベースエラー: リトライしない

## モニタリング

### メトリクス

以下のメトリクスを監視します。

- API レスポンスタイム
- エラー率
- ジョブの実行時間
- データベースのクエリ時間
- メモリ使用量

### ログ

以下のログを記録します。

- アクセスログ
- エラーログ
- ジョブログ
- API 呼び出しログ

### アラート

以下の条件でアラートを発行します。

- エラー率が閾値を超えた場合
- レスポンスタイムが閾値を超えた場合
- ジョブが失敗した場合
- ディスク使用率が閾値を超えた場合

## 災害復旧

### バックアップ戦略

以下のバックアップを実施します。

- データベースの日次バックアップ
- バックアップの保持期間は30日
- 異なるリージョンへのバックアップ保存

### 復旧手順

以下の手順で復旧します。

1. 障害の検出と通知
2. バックアップからのリストア
3. データの整合性確認
4. サービスの再開
5. 事後分析

### RTO と RPO

以下の目標を設定します。

- RTO（目標復旧時間）: 4時間
- RPO（目標復旧時点）: 24時間
